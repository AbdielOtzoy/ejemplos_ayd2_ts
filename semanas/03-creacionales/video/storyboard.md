# Storyboard — Factory Method

Video educativo con motion graphics vectoriales, paleta azul noche con acentos turquesa, coral y dorado. Los diagramas siguen el ejemplo `semanas/03-creacionales/codigo/factory-method.ts`.

| Tiempo | Escena | Visual | Narración |
|---|---|---|---|
| 00:00–00:20 | Introducción | Título sobre un fondo nocturno; los canales Email y SMS aparecen como opciones de producto. | Cuando una aplicación necesita enviar una notificación, ¿quién decide si debe crear un correo o un SMS? Esa decisión parece pequeña, hasta que aparecen más canales. Factory Method organiza la creación: CreadorNotificacion conserva el flujo común y trabaja con la interfaz Notificacion. |
| 00:20–00:49 | El problema | Un servicio acumula ramas para construir Email y SMS; cada canal añade otra dependencia. | Imaginemos que el método avisar contiene un if para Email y otro para SMS. En cada rama, el servicio construye una clase concreta. Ahora esa clase conoce los canales, los constructores y quizá sus detalles de configuración. La lógica de negocio empieza a depender de cada proveedor. Cada canal nuevo obliga a tocar esa misma clase. Si el proyecto crece, el if se extiende y una modificación puede afectar rutas que ya funcionaban. |
| 00:49–01:14 | La idea | El creador conserva avisar y delega crearNotificacion a una subclase. | Factory Method propone mover la decisión de creación a un método de fábrica. El creador conserva una operación común, pero no construye el producto directamente. Una clase creadora declara ese método; sus subclases lo redefinen para elegir qué notificación concreta entregar. Así, el flujo de envío permanece en un lugar, y la elección del producto cambia mediante el creador. |
| 01:14–01:40 | Participantes | Diagrama de clases: creador abstracto arriba y creadores concretos debajo. | En el ejemplo, Notificacion es la interfaz del producto. Declara enviar con un mensaje; avisar trabaja con ese contrato. EmailNotificacion y SmsNotificacion son productos concretos. Cada uno implementa enviar, aunque el canal real de entrega cambia. CreadorNotificacion es el creador. Define crearNotificacion y también la operación avisar, que contiene el trabajo común. |
| 01:40–02:06 | Producto | Notificacion declara enviar; Email y SMS implementan el mismo contrato. | En TypeScript, crearNotificacion está marcado como abstracto y protegido. La clase base no elige un canal; obliga a cada subclase a decidirlo. CreadorEmail redefine el método y devuelve un EmailNotificacion. CreadorSms hace lo mismo con SmsNotificacion. El tipo de retorno es Notificacion, así avisar usa enviar sin preguntar qué clase concreta recibió. |
| 02:06–02:30 | Recorrido | Secuencia cliente → creador → método de fábrica → producto → enviar. | Veamos el recorrido. El cliente crea un CreadorEmail y llama a avisar con el mensaje de confirmación del pedido. Avisar invoca crearNotificacion. Esa llamada llega a CreadorEmail, que produce el objeto EmailNotificacion. Después, avisar llama enviar sobre la interfaz Notificacion. El creador coordina la operación; el producto concreto realiza el envío. |
| 02:30–02:57 | Dos variantes | Dos creadores concretos producen productos distintos y comparten avisar. | Si el cliente usa CreadorSms, el mismo método avisar recorre la misma operación, pero el producto ahora es SmsNotificacion. Por eso, el cliente cambia de canal al elegir otro creador. La operación de negocio no necesita ramas para Email y SMS. En la demo, ambas llamadas muestran mensajes distintos en consola. En una aplicación real, enviar conectaría con el proveedor del canal. |
| 02:57–03:24 | Extensión | WhatsApp se incorpora como par de clases nuevas que respetan Notificacion. | Para sumar WhatsApp, crearíamos un producto WhatsAppNotificacion y un creador CreadorWhatsApp. Ambos respetan el contrato común. El resto del flujo puede seguir usando avisar y enviar. Agregar un canal significa extender las clases, no meter otra rama allí. Ojo: algún punto de entrada todavía debe elegir qué creador usar. Factory Method concentra la decisión; no la hace desaparecer. |
| 03:24–03:44 | Cuándo usarlo | Tres señales para elegir Factory Method: familias previstas, interfaz común y operación estable. | Conviene cuando la clase usa productos de una interfaz, pero cada variante necesita una forma distinta de crearse. También ayuda si esperamos nuevas variantes y queremos mantener estable la operación que trabaja con ellas. Funciona mejor cuando los creadores concretos encajan con la estructura de herencia que ya tiene el diseño. |
| 03:44–04:01 | Límite | La jerarquía de creadores tiene un costo; una fábrica simple puede bastar en casos pequeños. | El costo es crear una jerarquía de creadores, y conservar al menos un punto del programa que conozca cuál instancia concreta elegir. Si solo hay dos objetos muy simples y la lógica apenas cambia, una función de fábrica o un if pequeño puede resultar más directo. |
| 04:01–04:17 | Resumen | Recap visual de interfaz, método de fábrica, creador concreto y operación común. | Recuerda el recorrido: el creador declara el factory method, las subclases deciden el producto, y avisar llama a su interfaz común. El patrón es útil para variar la creación sin dispersar las dependencias sobre clases concretas. |

Duración final: 4.30 minutos. Subtítulos españoles quemados en el video y disponibles en `subtitulos.srt`.
